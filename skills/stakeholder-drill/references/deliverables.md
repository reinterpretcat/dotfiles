# Deliverables and portable context

Match the requested deliverable; these are shapes to adapt, not mandatory files or sections.

## Portable brief

A brief passed to a fresh reviewer should contain enough raw context to avoid dependence on the surrounding chat:

```text
Subject and user objective:
Decision this drill should inform:
Stage and relevant versions:
Authoritative sources and how to access them:
Scenario facts and explicitly hypothetical assumptions:
Requested perspectives or mode:
Scope, exclusions, permitted reads/runs/writes and effort:
Requested deliverable:
```

When reviewing an existing dialogue, include it as an assertion source, not as the ground truth. Keep earlier conclusions out of an independent verification brief unless comparing review history is itself the task. A reviewer without source access must narrow its claims rather than reconstruct unavailable evidence.

## In-chat drill

State the scenario assumptions briefly. Present a focused dialogue with persona names or roles, then evaluator notes distinguishing intended behavior from supported capability. End with the few findings that matter to the user's decision and any unresolved questions. Do not make every fictional utterance carry a technical citation; attach evidence to the evaluator's factual assessment.

## Cross-persona findings

Lead with the conclusion and what remains uncertain. Summarize what each role exposed, then distinguish factual corrections from design gaps. A compact finding record can use:

```text
Stakeholder need and scenario:
Claim or intended behavior:
Finding and practical consequence:
Evidence status, source and scope:
Minimal clarification or discriminator:
```

Use severity only when it helps the user's decision. “Not implemented” can be expected at the concept stage; it becomes a blocker when the current decision relies on it. A hypothetical scenario is not a roadmap commitment.

## Saved review

Use the project's established review location and conventions, or the user's chosen destination. A single report is usually sufficient. Include source references, evidence limits and enough context for another chat to understand the conclusion. Preserve supplied dialogues or link immutable originals when needed for traceability. Hash snapshots are optional when source drift or reproduced measurements make them useful, not required ceremony for every discussion.

Link the report from an existing project entry point when appropriate. Preserve existing task ownership and phase status; recording an idea does not schedule it. Do not create a competing specification or duplicate a maintained overview. Never store review artifacts alongside the globally reusable skill.

## Reply to the originating reviewer

Start with the useful questions. Group necessary corrections by role or theme, with exact sources for consequential claims. Explain what the evidence supports and what it does not; avoid attributing a stronger claim than the original text made. Request a revised, clearly scoped assessment or a discriminating example when appropriate.

Keep the reply ready to send, but sending it to another person or service is a separate action requiring the user's instruction. Providing text is sufficient when the user asks for a response.
